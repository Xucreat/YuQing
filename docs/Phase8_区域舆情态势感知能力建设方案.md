# Phase 8 区域舆情态势感知能力建设方案

> 适用对象：河北廊坊区域公安、政府社会治理与舆情研判人员  
> 文档性质：架构审计与实施方案设计。本次不修改应用代码、不新增数据库迁移、不执行数据变更。

## 1. 结论与建设边界

当前系统适合作为“河北廊坊区域网络信息监测与风险预警平台”的试点基础，能够支撑新闻、政务网站、RSS/搜索及微博正文的区域发现、初步研判、事件聚合、规则预警、人工状态处置和大屏展示。

但它尚不宜被定义为完整的“区域网络舆情态势感知平台”。原因不在于缺少大规模基础设施，而在于现有主数据仍是单条内容：微博评论被识别后跳过，用户与互动关系未保存，传播树由来源和时间顺序推导，事件风险取关联内容的最高单条风险。因此系统能够发现风险信息，尚不能稳定回答“群众怎么看、是否在扩散、谁在推动、处置是否有效”。

Phase 8 的目标不是建设商业全网舆情平台，而是将现有系统逐步升级为：

> 区域网络舆情风险预警与处置辅助系统。

优先解决廊坊县域场景最有价值的四个问题：民生投诉和热点是否升温、突发事件是否扩散、涉政务/涉警讨论是否恶化、官方处置后舆情是否回落。

## 2. 当前能力与差距

### 已具备能力

- 数据源配置与多类网页内容采集，具备运行批次、重复、失败、准入过滤等采集质量记录。
- `Opinion` 记录内容、来源、时间、地域、关键词、情感、风险、AI 摘要；微博正文另有作者显示名、外部 ID 和互动总数。
- `Event` 可聚合内容，提供主题、热度、趋势、状态和人工操作记录。
- 预警规则可按风险、关键词和来源生成告警；告警具备待处置、处理中、已解决、忽略、误报状态。
- 已有定时采集与定时预警评估，并通过 PostgreSQL advisory lock 避免多实例重复调度。

### 对区域政府使用仍不足的能力

- 群众态度：评论和回复未入库，无法观察支持、质疑、抱怨和诉求。
- 事件态势：事件没有“基本事实、影响对象、官方回应、处置责任、反馈效果”的结构化载体。
- 事件级风险：现有风险为关联内容最高分；单条高风险可抬高事件，数量、速度、负面比例、本地性和是否回应没有进入统一评分。
- 传播研判：当前传播节点没有真实转发、回复、账号关系证据，图形只能作来源时间序列展示，不应支持指挥决策。
- 处置闭环：状态和备注可用，但没有交办、责任单位、时限、反馈材料、复盘结论和误报原因沉淀。

### 当前不需要建设的能力

- 覆盖所有境内外平台的全网采集。
- 对个人进行画像、预测或自动风险处置。
- 复杂影响力排名、社群识别和跨平台关系图。
- 以实时流计算为目标的海量架构。

这些能力不能直接改善廊坊当前的研判和处置质量，反而会提升数据合规、接口稳定性和运维成本。

## 3. 事件级舆情模型演进

### 3.1 现状审查

`Opinion` 当前同时承担新闻文章、政府发布、微博帖子、分析结果、风险评分和有限互动快照，属于可支撑 MVP 的统一内容模型，但不适合继续承载评论、转发、政府回应和账号关系。

`Event` 是正确的系统中心，但目前更像“聚合结果”。它有成员内容、风险、热度、趋势和状态，缺少事件事实和处置对象。`AlertRecord` 已有最小处置状态，但以单条 `Opinion` 触发并在事后关联事件。`PropagationNode` 的 `parent_id` 无真实互动关系证据。`CollectorRun` 对采集质量足够，且已能记录发现但跳过的评论数；不应把它改造成业务事实表。

### 3.2 推荐的最小模型结构

不建议立即用六张全新社交模型替换现有模型。推荐保留 `Opinion`、`Event`、`AlertRecord`、`CollectorRun`，以“统一内容 + 有限补充实体”的方式渐进演进：

```text
Event
  ├─ EventOpinion ─ Opinion（新闻 / 微博正文 / 政府回应，统一内容入口）
  ├─ EventComment（群众评论或回复，按 event_id 直接关联）
  ├─ EventOfficialResponse（官方回应、办理进展、结果）
  ├─ EventTask（交办与反馈，后续阶段）
  └─ EventReview（复盘，后续阶段）

Opinion ── optional ── AccountSnapshot
Opinion ── optional ── InteractionSnapshot（按采集时间保存计数变化）
EventComment ── optional ── AccountSnapshot
```

建议字段如下，均为后续实施建议，非本次数据库变更：

| 实体 | 最小字段 | 目的 |
|---|---|---|
| `Opinion` | 保持现有；补充 `content_kind`、`platform`、`source_external_id`、`official_flag` | 统一文章、帖子和正式回应，不打破既有列表和事件关联 |
| `EventComment` | `platform`、`comment_id`、`event_id`、`opinion_id`、`parent_comment_id`、`content`、`author_id/hash`、`author_name`、`publish_time`、`sentiment`、`relevance` | 将评论视为事件态度证据，而不是独立风险主体 |
| `AccountSnapshot` | `platform`、`account_id`、`display_name`、`verified_type`、`follower_count`、`captured_at` | 支持来源可信度和关键账号识别；不保存非必要个人资料 |
| `InteractionSnapshot` | `opinion_id`、`captured_at`、`like_count`、`comment_count`、`repost_count` | 用增量而不是单次总量判断升温 |
| `EventOfficialResponse` | `event_id`、`opinion_id`、`publisher`、`response_type`、`publish_time`、`summary`、`url` | 将权威回应与群众讨论放入同一事件，但语义明确区分 |

`Content`、`Post`、`Comment`、`Account`、`Interaction`、`Relation` 不应一次性全量拆分。Phase 8 只需要独立“评论、账号快照、互动快照、官方回应”四类补充事实；`Opinion` 仍是文章和帖子统一索引。只有在取得稳定转发明细后，才评估 `Relation` 或 `Repost` 明细模型。

### 3.3 统一关联规则

新闻、微博正文和政府回应仍先进入 `Opinion`，通过现有 `EventOpinion` 关联事件。微博评论不参与当前的全局事件自动聚合：先根据其所属微博的 `opinion_id` 继承事件；无所属微博时，进入“待归属评论”队列，由规则或人工挂接。政府回应以 `official_flag=true` 和 `response_type` 标识，并由研判人员确认关联事件。

该设计避免评论因词汇命中被误建成新的社会事件，同时让同一事件具有“事实来源、群众态度、官方回应”三类可区分证据。

## 4. 区域数据能力优先级

### 第一优先级：微博评论

应作为下一阶段最高优先级，但前提是通过合法、稳定、可审计的数据接口取得。县域场景中，评论比扩展更多新闻站点更直接反映群众态度、诉求和争议点。

最低采集字段为：`platform`、`comment_id`、`post_id/opinion_id`、`parent_comment_id`、`content`、`author_id 或脱敏稳定标识`、`author_name`、`publish_time`、`like_count`、`captured_at`。`event_id`、情感、立场和相关性应由系统处理后写入，不能将采集器识别结果当作事实。

先覆盖评论正文和一级回复即可。评论的业务角色是“事件态度证据”，需要单独统计负面比例、主要诉求、重复观点和新增速度；不应单条触发高等级告警，除非达到明确的涉警、公共安全等人工复核规则。

### 第二优先级：互动变化

现有微博互动是帖子上的总量 JSON 值。应升级为定时快照，计算：

- 近 1 小时、6 小时、24 小时的点赞/评论/转发增量；
- 增量相对该事件过去 7 天日均值的倍数；
- 多条帖子的互动是否集中于同一事件；
- 官方回应发布前后，新增讨论和负面比例是否变化。

互动数据用于“热度”和“上升趋势”，不能直接等同于风险。点赞可能是支持、围观或情绪表达；转发总量也可能来自官方发布。因此应设上限，并要求与内容数量、负面比例、本地相关性共同解释。

### 第三优先级：用户基础信息

需要最小账号信息，但无需建设个人画像系统。推荐仅保存账号显示名、平台账号稳定标识、认证类型、粉丝量级、账号类型（官方/媒体/普通/未知）和采集快照时间。

用途是：识别官方发布、区分媒体报道与群众表达、在事件页展示高影响或高互动账号、为人工核验提供入口。粉丝数应使用分级或区间，避免把精确值误用为社会影响力结论。不得基于个人信息自动认定风险人物或开展画像推断。

### 暂缓：视频、OCR、ASR、知识图谱、社交关系图谱

视频平台和 OCR/ASR 需要稳定授权数据源、多模态质量治理及更高存储成本；在微博评论未打通前，优先级较低。知识图谱需要高质量实体、关系和持续维护，当前事件与账号事实尚不完整。社交关系图谱依赖粉丝/关注/转发明细，当前没有合法稳定的数据基础，容易产生不可靠结论。上述能力均应在主平台互动闭环验证价值后再评估。

## 5. 事件中心升级设计

以“某小区停水”为例，事件页应按事实、态势、处置三层组织，而不是增加复杂卡片：

| 区域 | 必须建设 | 重要建设 | 暂缓建设 |
|---|---|---|---|
| 基本事实 | 事件标题、首次/最近时间、涉及区县、主题、事实摘要、来源数量 | 影响小区/单位、事实核验标签 | 自动事件真伪判定 |
| 舆情态势 | 内容趋势、评论数量、负面/中性/正面占比、热点词、来源分布 | 主要诉求聚类、互动增量、跨来源同步 | 社群网络图 |
| 风险研判 | 事件总分、等级、分项解释、升/降温原因 | 历史相似事件参考 | 黑箱预测模型 |
| 关键主体 | 官方账号/媒体/高互动账号列表 | 账号认证和粉丝量级 | 个人影响力画像 |
| 官方回应 | 回应状态、发布时间、链接、办理摘要 | 多轮办理进展 | 自动生成对外回应 |
| 处置 | 当前状态、责任单位、负责人、时限、处置记录、反馈结论 | 催办与逾期提醒 | 跨部门自动派单 |

传播页在没有真实转发/回复关系前，应更名或表述为“来源与时间分布”，并在页面标注为推断关系，不应显示为真实传播链。获得转发明细后再恢复真实传播网络展示。

## 6. 可解释的事件级风险评分

现有“关键词 + 情感 + 单条规则分”可保留为内容级准入和初筛。事件级评分应独立计算，推荐 0-100 分的可解释加权规则：

```text
事件风险分 =
  内容风险基线（0-25）
+ 扩散与增长（0-20）
+ 群众负面态度（0-20）
+ 本地相关性与影响范围（0-15）
+ 事件类型严重度（0-15）
+ 官方回应修正（-10 至 +5）
+ 历史相似事件修正（0-5）
```

建议分项口径：

- 内容风险基线：不取单条最高分，而是取高风险内容占比与最高分的封顶组合，防止单条误判支配事件。
- 扩散与增长：近 24 小时新增内容、评论和互动增量相对前 7 天平均值；样本过少时标记“数据不足”，不强行判升温。
- 群众负面态度：仅用已关联、相关性合格的评论计算；同时展示样本量，样本不足不加分。
- 本地相关性：廊坊、区县、街道、具体小区/单位命中以及人工确认；全国新闻转载不得仅因包含地名而高分。
- 事件类型严重度：公共安全、群体性风险、涉警、涉政务、民生服务等由可维护词表和人工确认共同决定。
- 官方回应修正：仅在回应已发布、内容与事件明确关联且人工确认后生效；回应不能机械“降风险”，若回应后负面持续增长，应不降反升。
- 历史相似事件：仅作为提示项，例如近 90 天同区域同主题反复出现；不作为自动定性依据。

每次评分应输出 `score_version`、`calculated_at` 和 `factors`（JSON 解释项）。告警应由事件风险、增长阈值、事件类型和人工确认共同触发，逐步从“单条告警”转为“事件告警”。

## 7. 政府处置闭环

现有事件状态、告警状态和操作日志是良好起点，但尚不能支撑政府交办。推荐流程：

```text
发现 → 研判 → 事件确认 → 预警 → 交办 → 处理中 → 反馈核验 → 复盘归档
```

建议最小字段与页面：

| 环节 | 最小新增事实 | 页面/交互 |
|---|---|---|
| 研判 | 研判结论、研判人、确认时间、是否误报 | 事件详情“研判”区 |
| 预警 | 事件告警等级、触发因素、通知范围、确认时间 | 预警详情，保留原单条告警链路 |
| 交办 | 主责单位、协办单位、负责人、截止时间、交办说明 | 事件详情“处置任务”区 |
| 处理 | 处理进展、措施、材料链接、更新时间 | 时间线与处理记录 |
| 反馈 | 官方回应、群众后续态度、是否回落、核验人 | 反馈核验区 |
| 复盘 | 结果、误报原因、处置时效、规则优化建议 | 归档事件的复盘页/报告 |

先在 `Event` 及其附属动作/任务记录上实现，不应把交办字段塞入 `AlertRecord`。告警只是发现信号，事件才是处置对象。对已存在的 `EventAction`，可保留状态变更与备注历史；后续用独立任务记录承载责任单位、期限、回执和材料，避免动作日志被当作业务台账。

## 8. Phase 8 实施路线

### Phase 8-A：事件态势口径与页面收口

- 目标：统一“内容级、事件级、告警级”概念；明确传播图为推断时间关系；补齐事件页现有数据的风险、热度、趋势解释。
- 修改范围：需求规格、接口契约、事件详情和大屏展示口径；复核现有 `Opinion/Event/AlertRecord/Propagation/CollectorRun` 的字段用途。
- 数据库影响：本设计阶段无；后续若保存事件评分解释，才增加 `Event` 评分版本/因素字段或独立快照表。
- 后端影响：事件聚合、热度、风险服务增加只读解释输出；不得改变既有告警兼容语义。
- 前端影响：事件详情增加“评分依据、数据样本量、来源时间分布、处置状态”信息区；传播页加推断声明。
- 风险：展示口径变化会影响用户理解，需与业务人员共同验收词汇。
- 优先级：P0。

### Phase 8-B：微博评论与互动快照最小闭环

- 目标：合法接入微博评论/一级回复，形成事件群众态度和互动增量，不将评论作为独立事件主体。
- 修改范围：采集器字段映射、评论去重和准入、评论关联规则、互动快照任务、事件态度统计。
- 数据库影响：后续实施建议新增 `EventComment`、`InteractionSnapshot`；本方案不创建迁移。保留 `Opinion.engagement` 兼容历史数据。
- 后端影响：采集质量增加评论拉取/入库/关联指标；事件服务提供评论统计、样本量和热点诉求接口；权限与审计覆盖人工挂接。
- 前端影响：事件详情增加“群众态度”页签，显示评论量、情感分布、代表性评论、最新增量和人工纠错入口。
- 风险：平台授权稳定性、评论噪声、个人信息最小化、采集失败导致趋势失真。需保存采集时间并显示“数据不完整”。
- 优先级：P0。

### Phase 8-C：可解释事件级风险与事件预警

- 目标：以事件而非单条内容为主风险对象，形成数量、增长、负面比例、本地性、类型、官方回应的可解释分项。
- 修改范围：事件风险服务、热度服务、告警评估、事件评分解释、阈值配置和测试样本。
- 数据库影响：后续建议增加事件评分版本、计算时间、因素快照；本方案不创建迁移。历史事件按兼容规则回退现有分数。
- 后端影响：保留单条规则预警，新增事件预警并通过去重/抑制规则避免同一事件重复轰炸；官方回应只作为受控修正项。
- 前端影响：事件中心展示总分和分项；预警中心区分“内容告警”和“事件告警”，提供触发证据链接。
- 风险：阈值未经本地样本校准会导致误报。应先灰度运行、人工对照 4-8 周后再作为主要告警依据。
- 优先级：P1。

### Phase 8-D：交办、反馈与复盘辅助

- 目标：把事件状态升级为可追溯的处置辅助闭环，不做自动行政决策。
- 修改范围：事件任务、官方回应、反馈核验、复盘记录、报表和权限边界。
- 数据库影响：后续建议增加 `EventTask`、`EventOfficialResponse`、`EventReview` 等小表；本方案不创建迁移。
- 后端影响：任务状态机、责任人/单位、到期提醒、回执和审计；所有状态变化保留操作日志。
- 前端影响：事件详情增加研判、交办、处理、反馈、复盘时间线；管理端增加待办和逾期视图。
- 风险：责任单位和处置材料属于业务敏感数据，须明确 RBAC、日志留存范围和导出权限。
- 优先级：P1，宜在 8-B 与 8-C 稳定后实施。

## 9. 风险控制与验收建议

- 数据合规：仅接入有合法授权的数据，账号信息最小化采集；稳定标识可脱敏或散列；设置保存期限、访问权限和导出审计。
- 事实可信：新闻、群众评论、官方回应必须在模型和页面中明确来源类别，AI 输出不得作为事实结论。
- 人工兜底：高风险事件、涉警、涉政务、公共安全类告警必须人工确认后交办；不得自动生成对外回应或自动升级行政处置。
- 指标校准：以廊坊真实历史事件建立小样本人工标注集，持续统计事件合并准确率、告警误报率、研判时效、处置闭环率和回应后回落率。
- 可用性：评论缺失、接口限流、采集延迟必须在事件页展示数据新鲜度和样本量，禁止用不完整数据得出“舆情平稳”结论。
- 渐进发布：每个阶段先做影子计算或只读展示，再由研判人员确认后启用预警和处置影响。

## 10. 明确禁止的过度建设

| 暂不建设项 | 原因 |
|---|---|
| Elasticsearch | 当前 PostgreSQL 足以支撑区域试点的结构化查询和全文能力；先验证数据量与检索瓶颈 |
| Kafka、Flink、复杂流计算 | 采集频率和处理规模尚不构成刚性需求，增加运维与故障面 |
| 微服务拆分 | 当前 FastAPI 单体分层清晰，Phase 8 的核心是数据语义和流程，不是服务拆分 |
| 图数据库 | 尚无真实转发/关注关系数据，建图会放大伪关系风险 |
| 全网爬虫 | 合规和稳定性风险高，且不符合区域场景“重点平台、重点事件”策略 |
| 自动化 AI 决策/自动回应 | 风险定性、交办和对外回应必须保留人工责任链 |
| 多租户 | 当前用户是同一地区政务体系，优先做 RBAC、单位责任和审计即可 |
| 全量个人画像 | 对区域治理价值有限且合规风险高；仅保留与事件研判必要的账号基础快照 |

## 11. 预期成熟度

完成 Phase 8-A 与 8-B 后，系统可从“网络信息监测系统”提升为具备群众态度和事件态势基础的区域舆情分析系统。完成 8-C 与 8-D、并经本地样本校准后，可达到面向廊坊实际工作可用的 L4 初级：区域网络舆情风险预警与处置辅助平台。

该目标不以商业舆情平台的全网覆盖为标准，而以“发现及时、研判有据、交办可追、反馈可验、复盘可用”为验收准则。
