## 结论摘要

- **八爪鱼真实能力结论**：已确认 `/data/notexported` 支持 `size` 限制返回条数；没有获得可依赖的分页或游标机制证据。当前测试环境的 API Key 已失效，故本次不能完成 `pageIndex`、`offset`、`skip`、`cursor`、`start`、`limit` 的有效响应比较。
- **ack 语义**：未验证。没有可创建且隔离的测试任务，也没有调用 `POST /data/notexported/update`。不能从请求体只有 `{taskId}` 推断它是批次确认还是任务级确认。
- **历史数据接口**：仓库存在一个未接入生产链路的只读诊断脚本，曾尝试 `GET /data/all?taskId&size&page`；它没有在非空任务上得到过有效响应，也没有找到八爪鱼官方参数文档。因此不能作为可用的历史消费接口。
- **最终建议**：**不建议开启** `data_sources.weibo_octopus.enabled=True`。现有实现对超过单次返回上限的未导出队列只能延迟确认，无法推进队列；如果供应商确认 update 是任务级确认，则任何绕过延迟确认的实现都有丢失未返回记录的风险。

## 1. 当前支持接口列表

审计对象：[weibo_octopus_collector.py](C:/Users/Administrator/Desktop/YQ/backend/app/collectors/weibo_octopus_collector.py)。生产采集器只封装以下三个接口：

| URL | 方法 | 参数/请求体 | 响应消费结构 | 当前用途 |
|---|---|---|---|---|
| `/token` | POST | JSON：`username`、`password`、`grant_type=password` | `data.access_token`、`data.expires_in` | 仅在未配置 `BAZHU_API_KEY` 时换取 Bearer token |
| `/data/notexported` | GET | query：`taskId`、`size` | `data.total`、`data.data` 或 `data.dataList` | 拉取未导出数据；采集器记录总数和本次返回数 |
| `/data/notexported/update` | POST | JSON：`{ "taskId": "..." }` | 仅检查 HTTP 200，不解析业务字段 | 入库成功后确认已导出 |

生产封装中**不存在** `page`、`pageIndex`、`offset`、`skip`、`cursor`、`start`、`limit` 参数，也不存在 `history`、`export`、`data/all` 或任务执行批次接口。配置只能覆盖三个路径，不能为 `/data/notexported` 增加受支持的分页协议。

## 3. 《八爪鱼ack语义验证报告》

### 执行情况

- 未创建测试任务：当前代码和配置没有任务创建接口或隔离任务凭据。
- 未调用 `POST /data/notexported/update`。
- 未对生产微博任务做任何确认操作。

### 结论

**情况 C：无法判断，需要官方确认或隔离任务实测。**

代码显示请求体只有 `{taskId}`，并未传递记录 ID、页号、游标、导出批次或本次返回记录集合。因此它的语义可能是任务级确认，也可能是服务端维护的隐式导出批次确认；仅凭客户端代码不能区分。

现有延迟 ack 防护逻辑是正确的保守行为：当 `returned < total` 时不调用 update。它不能让队列前进，也不能证明后续数据可消费。

## 5. 三个消费方案评估

| 方案 | 实测适配性 | 1000 条/小时结论 |
|---|---|---|
| A. `/data/notexported` + 延迟 ack | `size` 可限制到 1000；已知 `total=4034` 时无可靠翻页，代码会拒绝确认 | 不支持稳定全量消费。每小时产出 1000 条且存在积压时，消费者每次重复拿到首批并持续 deferred |
| B. 历史数据接口 | `/data/all` 仅有空任务历史结果，未证实真实分页、时间范围、批次或一致性 | 当前不具备采用条件。若供应商提供可分页/按执行批次查询的只读正式接口，优先评估此方案 |
| C. 本地消费状态表 | 可以记录已入库 external_id/游标，但不能取得未返回的后续记录，也不能安全替代供应商 ack | 不能解决上游无分页和未知 ack，当前不应作为独立补救方案 |

## 6. 推荐架构与上线决策

### 推荐架构

当前不继续 `notexported` 消费模式，也不切换到未经验证的 `/data/all`。先向八爪鱼取得以下书面接口契约，随后使用隔离任务完成只读分页与 ack 实验：

1. `/data/notexported` 的最大 `size`、分页或 cursor 参数、排序和快照一致性。
2. `/data/notexported/update` 是否按整个 `taskId` 清空，及是否支持记录/批次/游标级确认。
3. 历史结果接口的正式 URL、时间范围/执行批次过滤、分页方式和保留期。
4. 用 10 条以内隔离任务验证 update 前后 `total` 与记录集合的变化。

### 是否可以开启

**不建议开启。**

依据：当前认证失败、待消费总量已经大于单批上限、无可靠分页、ack 语义未知，任一条件都不足以保证“每小时生产 1000 条，系统每小时全量进入 Opinion/Risk/Event/Alert”。

## 7. 后续修改范围（仅在供应商能力确认后）

若确认可靠分页和批次/记录级 ack：

- 文件范围：`backend/app/collectors/weibo_octopus_collector.py`、相关单测 `backend/tests/test_weibo_octopus_collector.py`；必要时更新 `backend/scripts/weibo_task_data_readonly_diag.py` 为非生产验收工具。
- 数据库迁移：只有供应商提供可持久化游标或批次 ID、且需要跨进程断点续取时才需要增加消费状态表及 Alembic migration；若仅依赖供应商 token/cursor 且能重复读取，现有 `external_id` 去重可能足够。
- 其他数据源：微博已由独立 `weibo_consumer` 调度隔离。只要修改保持在微博 collector 和其配置范围，不影响其他数据源。

若只确认任务级 ack 且仍无可靠分页：不应通过本地状态表、提高 size 或调整 cron 绕开限制；这些措施不能防止未返回记录被任务级确认清除。
