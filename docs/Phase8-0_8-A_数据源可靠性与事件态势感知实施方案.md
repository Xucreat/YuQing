# Phase8-0_8-A 数据源可靠性与事件态势感知实施方案

> 适用场景：河北廊坊区域公安、政府舆情研判与社会治理人员  
> 文档性质：代码审计、架构设计与后续实施规划。本文不修改代码、不新增数据库迁移、不执行数据变更。

## 1. 当前架构评估

### 1.1 现有架构适用性

现有 FastAPI + SQLAlchemy + PostgreSQL 单体架构适合作为廊坊区域试点。当前系统已经形成：

```text
DataSource → CollectorService → Opinion → AI/规则研判
                                      ↓
                                  Event / AlertRecord
                                      ↓
                              Vue 事件中心 / 指挥大屏
```

它能够支撑新闻、政府网站、RSS/搜索和微博正文的区域信息发现、初步风险筛选、事件聚合、告警和人工状态记录。对县域用户而言，当前最重要的架构问题不是吞吐量，而是两类事实没有被明确区分：

- 采集任务事实：某次任务是否成功、得到多少数据、是否确认上游导出。
- 数据源健康事实：某个源目前是否可用、是否持续失败、是否长期无有效数据。

`CollectorRun` 适合第一类，不应被直接当作第二类。`DataSource` 已有 `last_run_at/last_status/last_error` 缓存字段，但代码审计未发现采集服务稳定写回这些字段的路径；管理接口主要根据 `CollectorRun` 最新记录计算 `latest_run_status/latest_run_at`。因此现在只能看到最近一次运行结果，不能可靠回答“微博八爪鱼是否已经持续失效”“某源是否超过监测时限没有数据”。

### 1.2 事件能力基线

`EventOpinion` 已提供事件与 `Opinion` 的多对多关系，并有 `(event_id, opinion_id)` 唯一约束，足以作为事件成员索引。`Event` 已有标题、描述、主题、地域、风险、热度、趋势、状态、成员数量及首末时间，适合作为系统核心对象。

当前仍存在三个限制：

1. 事件风险服务取关联 `Opinion.risk_score` 的最大值，事件容易被一条误判内容支配。
2. 热度服务使用成员数量、近 24 小时新增和互动总量的简单封顶加权；没有保存每次计算的依据快照。
3. `AlertRecord` 先按单条 `Opinion` 触发，随后才尝试回填事件；预警对象仍偏向内容而非事件。

本阶段不依赖新增微博评论，先利用现有新闻、政务网站和历史微博数据，补强“事件画像、风险解释、来源态势和处置可见性”。

## 2. Phase 8-0 数据源可靠性治理

### 2.1 当前健康能力评估

| 健康问题 | 当前能否识别 | 现有依据 | 结论 |
|---|---|---|---|
| Token 失效 | 部分能 | 八爪鱼采集器在 HTTP 非 200 或缺少 token 时抛出异常；`CollectorRun` 可记失败及错误信息 | 能在任务级发现，不能形成标准化 `TOKEN_EXPIRED` 状态 |
| 连续失败 | 不能直接识别 | 可查询历史 `CollectorRun` | 需要按数据源聚合连续失败次数 |
| 长时间无数据 | 不能可靠识别 | 有 `fetched_raw/upstream_returned/created`，但没有源级无数据阈值和最后有效数据时间 | 需要区分“任务成功但无数据”和“接口失败” |
| 接口异常 | 部分能 | `status/error_msg`、上游返回量和失败计数 | 缺少错误分类、HTTP 状态和重试后的最终原因 |
| 采集质量下降 | 只能事后查询 | 有重复、准入过滤、评论跳过、未确认等批次指标 | 没有源级基线、质量比率和降级判定 |
| 采集延迟 | 部分能 | `start_time/end_time` | 无稳定的源级延迟目标和最近延迟统计 |

八爪鱼 Token 过期时，推荐把错误分类为“认证不可用”，而不是普通的采集失败。这样管理员能看到可执行原因，并避免工作人员误以为“微博没有舆情”。

### 2.2 轻量健康状态模型

#### 建议优先复用现有字段

后续实现时，优先使用 `DataSource` 已有字段：

- `last_run_at`：最近一次任务开始时间或结束时间，统一口径后使用。
- `last_status`：源级摘要状态，不等同于批次 `CollectorRun.status`。
- `last_error`：最近一次经过脱敏和截断的错误摘要。

这三个字段当前已可被管理接口序列化，但需要在采集任务结束时统一写回，并由单一服务负责计算，避免 API 查询和调度器各自推断。

#### 建议新增字段（后续迁移，仅作设计）

如果确认允许新增一组极小字段，建议只增加：

| 字段 | 是否必要 | 含义 |
|---|---|---|
| `health_status` | 必要 | `healthy / degraded / unhealthy / paused / unknown` |
| `last_success_at` | 必要 | 最近一次任务成功且完成有效处理的时间 |
| `last_failure_at` | 必要 | 最近一次最终失败时间 |
| `consecutive_failures` | 必要 | 连续最终失败次数，成功后归零 |
| `last_error_code` | 必要 | 标准化错误码，如 `TOKEN_EXPIRED`、`AUTH_FAILED`、`TIMEOUT`、`HTTP_5XX`、`PARSE_ERROR`、`NO_DATA` |
| `last_error_message` | 可选 | 面向管理员的脱敏摘要；可复用 `last_error`，不要重复存储 |
| `last_valid_item_at` | 重要但可后置 | 最近一次产生至少一条通过准入的有效内容 |
| `health_updated_at` | 重要但可后置 | 健康状态计算时间，避免把旧状态误认为当前状态 |

不建议增加 `failure_history`、`health_score`、复杂告警规则 JSON 或单独监控服务。失败历史已由 `CollectorRun` 保存；健康状态是可重算的摘要，不应成为第二套日志系统。

#### 状态判定规则

推荐使用明确、可解释的优先级：

```text
paused       管理员主动停用，最高优先级
unhealthy    TOKEN_EXPIRED/AUTH_FAILED，或连续最终失败 >= 3
degraded     任务成功但长期无有效数据，或质量/返回量连续低于基线
healthy      最近一次成功，且没有超出无数据窗口
unknown      从未运行、历史状态缺失或健康信息过期
```

阈值应按源类型配置在应用设置或代码常量中，而不是先做复杂的逐源规则表：微博可按 1 小时或 1 个消费周期判断无数据，新闻/政府网站按 24-48 小时判断。`NO_DATA` 只有在源应有更新且连续发生时才降级，不能把节假日或源本身低频误判为故障。

### 2.3 采集失败处理策略

推荐“记录失败 + 标准化健康状态 + 管理员提醒 + 有限自动降级”，不推荐立即自动暂停所有失败源：

1. 第一次失败：保留当前调度，记录 `last_error_code` 和失败日志。
2. 连续两次失败：状态变为 `degraded`，管理员列表显示提醒。
3. Token/认证错误或连续三次最终失败：状态变为 `unhealthy`，停止该源的自动重试风暴；下一调度周期只做一次低频探测。
4. 管理员确认修复或测试采集成功：恢复 `healthy`，连续失败归零。
5. 其他来源继续运行；单一源失效不能阻断整个批次，也不能把缺失源解释为区域舆情平稳。

“自动暂停”只对认证失败、明确不可恢复配置错误和达到连续失败阈值的源生效；“降低频率”用于状态为 `unhealthy` 的探测，而不是长期静默。所有状态变化应写入现有操作日志或采集日志，便于审计。

### 2.4 管理页面设计

#### 数据源列表

在现有 `Sources.vue` 列表增加以下只读列：

- 健康状态：正常、降级、异常、暂停、未知。
- 最近成功：`last_success_at`，没有时显示“从未成功”。
- 最近失败：`last_failure_at`。
- 连续失败：次数。
- 最近错误：标准码 + 简短原因。
- 最近有效数据：如尚未实现，显示“未统计”，不能显示为 0。

微博八爪鱼示例应呈现为：

```text
微博八爪鱼  | 异常
原因：TOKEN_EXPIRED（访问令牌失效）
最近成功：2026-07-28 10:15
连续失败：3
建议：更新凭证后执行一次测试采集
```

#### 数据源详情/运行记录

保留现有运行历史，增加按 `error_code`、状态和时间筛选；在详情顶部展示健康摘要，在下方展示批次事实。不能用“最近一次任务 success”覆盖健康摘要，也不能用健康摘要替代原始批次记录。

#### 后端接口建议

不新增独立监控服务，沿用 `/admin/data-sources`：

- `GET /admin/data-sources`：在现有序列化结果中增加健康字段。
- `GET /admin/data-sources/{id}/runs`：保留批次明细，增加标准化错误码和结束时间（若当前结构允许只读派生）。
- `POST /admin/data-sources/{id}/test`：后续可增加一次受权限保护的轻量连接/认证测试，不拉取大量数据。
- `POST /admin/data-sources/{id}/health/ack`：可选，用于管理员确认已知故障；不改变历史运行记录。

新增或扩展接口必须使用现有 `sources:read`、`sources:write`/管理员权限和审计写入。测试采集、凭证修改和启停操作不能向普通研判人员开放。

## 3. Phase 8-A 事件态势感知

### 3.1 Event 是否适合作为核心对象

适合。`Event` 已通过 `EventOpinion` 与内容关联，前端详情已有标题、风险、热度、趋势、成员数量、首末时间和操作记录，后端也有聚合、热度和风险服务。Phase 8-A 不应重建事件中心，而应把 `Event` 从“内容聚合结果”收口为“研判工作对象”。

建议把事件信息分为三层：

```text
事件事实：发生了什么、在哪里、何时、依据是什么
事件态势：信息量、来源、趋势、热度、关键词、风险因素
事件处置：当前状态、人工记录、官方回应（现阶段可先展示占位）
```

### 3.2 现有模型审查

| 模型 | 当前作用 | Phase 8-A 判断 |
|---|---|---|
| `Opinion` | 统一保存文章/微博正文及内容级分析 | 保留；不再向其中塞入事件事实和处置字段 |
| `EventOpinion` | 事件成员关系，已有唯一约束 | 保留；作为所有来源内容进入事件的统一入口 |
| `Event` | 聚合、风险、热度、趋势、状态 | 保留并补充只读态势解释，后续再考虑小量事实字段 |
| `AlertRecord` | 单条规则命中与处置状态 | 保留兼容；Phase 8-A 不把它改成事件表 |
| `PropagationNode` | 由时间和来源推导的节点 | 保留历史接口，但重新标注为来源时间分布 |
| `CollectorRun` | 每次采集批次质量和失败事实 | 保留；不与事件模型耦合 |

### 3.3 事件详情页画像

以“某小区停水事件”为例，事件页建议如下：

#### 必须建设

- 基本信息：事件名称、事实摘要、首次发现、最近更新时间、涉及区县/街道、内容来源数量。
- 舆情态势：关联内容数量、按来源分布、按日/小时趋势、当前热度、趋势状态、热点关键词。
- 风险解释：总风险等级、内容风险最高项、数量和增长贡献、地域命中、事件类型、数据时间窗口和样本量。
- 当前处置：事件状态、操作记录、最近一次人工研判、官方回应“未发现/待核验”状态。
- 数据可信提示：参与计算的内容时间范围、采集新鲜度、是否存在失效数据源。

#### 重要建设

- 事件事实时间线：按内容时间列出最早报道、关键进展和权威发布。
- 来源分层：政府/官方、新闻媒体、微博正文、其他来源分开统计。
- 风险对比：当前分数与前一个计算窗口相比的变化及原因。
- 代表性内容：按权威性、风险、时间和热度选取，提供原文链接。
- 处置备注与人工标签：民生、涉警、涉政务、公共安全、待核验等。

#### 暂缓建设

- 自动生成事实真相结论。
- 关键人物画像、社群关系图和真实传播链。
- 未有稳定数据支撑的“影响人数”估算。
- 复杂知识图谱和多模态视频分析。

### 3.4 Event 风险评分框架

内容级 `Opinion.risk_score` 继续用于准入、排序和单条证据解释。事件级风险单独计算，兼容现有 0-100 字段：

```text
EventRisk = clamp(
    0.30 * ContentRisk
  + 0.20 * Volume
  + 0.20 * Growth
  + 0.15 * Locality
  + 0.15 * EventType,
  0, 100
)
```

各分项均归一化为 0-100：

- `ContentRisk`：关联内容风险的高分占比、均值和最高分的封顶组合；不再直接等于最高单条分。
- `Volume`：事件内容量相对区域同类事件的分级值；小样本不得直接给高分。
- `Growth`：最近 24 小时新增量与前 7 日平均新增量的比值；无历史基线时标记未知并降低权重。
- `Locality`：廊坊、区县、街道、具体小区/单位命中及人工确认结果。
- `EventType`：公共安全、突发事件、涉警、涉政务、民生服务等可维护规则类别。

现阶段不纳入微博评论和转发数据，公式保留未来接口：

```text
未来扩展项 = InteractionGrowth + NegativeAttitude
```

当互动数据真实可用后，按重新校准后的权重替换或挤占 `Volume/Growth`，不能直接叠加造成双重计分。官方回应不应在本阶段自动降低分数；可先作为事件详情中的解释字段，待处置闭环建立后增加受控修正。

每次计算应返回（或后续保存）`score_version`、计算时间、窗口、分项值、缺失数据说明和触发原因。若暂不新增字段，先由 API 组装只读 `risk_factors`，不修改历史分数语义。

事件等级建议保持现有兼容阈值：`<40 low`、`40-69 medium`、`>=70 high`。`critical` 仍由明确的严重事件规则和人工复核产生，不因事件内容量自动升级。

### 3.5 传播分析重新定位

当前 `PropagationNode` 通过同来源上一节点或时间上一个跨来源节点生成 `parent_id`，没有转发 ID、回复 ID、账号关系或平台证据。因此它不是真实传播链，最多是“事件来源时间分布”。

Phase 8-A 的页面建议：

- 将“传播分析”标题改为“来源与时间态势”（或在页面明确标注“推断关系”）。
- 优先展示来源数量、首发时间、时间序列、来源占比、内容风险分布和趋势。
- 不展示“某来源传播给某来源”的确定性文案，不用深度值推断传播层级。
- 保留接口兼容和历史数据，避免本阶段重算为伪真实关系。

未来取得合法的微博转发/回复明细后，再引入明确的 `relation_type`、`platform_relation_id`、`actor_id` 和证据时间，单独升级真实传播展示；当前不引入图数据库。

## 4. 数据模型演进建议

### 4.1 本次设计阶段不执行的变更

- 不新增 Alembic migration。
- 不改变现有表约束、`Opinion` 字段含义、`AlertRecord.handled` 兼容字段和 `EventOpinion` 唯一约束。
- 不回填历史事件或重算生产数据。
- 不把健康状态、事件事实和评分解释临时写入无关 JSON 字段作为永久方案。

### 4.2 后续实现的最小变更包

**Phase 8-0 后续迁移候选：** `DataSource.health_status`、`last_success_at`、`last_failure_at`、`consecutive_failures`、`last_error_code`，可选 `last_valid_item_at/health_updated_at`。`CollectorRun` 增加标准化 `error_code` 的候选字段，或在不改表的情况下先由服务层从错误文本映射。

**Phase 8-A 后续迁移候选：** 不新增事件主表，优先让 API 提供只读态势结构；只有需要持久化评分历史时，才增加 `event_risk_snapshots` 或受控的事件评分解释字段。事件事实、官方回应、交办任务不属于本 Phase 8-A 的强制数据库范围。

### 4.3 事件与来源统一关联

新闻、政府网站和历史微博正文继续进入 `Opinion`，由现有 `EventOpinion` 关联事件。事件详情通过关联内容计算来源数量、时间趋势、热点关键词和风险依据。政府回应在未来仍建议先作为带 `official` 类型的 `Opinion`，经人工确认后关联事件；不要立即为回应建立复杂独立业务域。

## 5. 后端、前端与 API 改造建议

### 5.1 Phase 8-0 后端

涉及模块：

- `app/models/data_source.py`：后续健康字段设计。
- `app/models/collector_run.py`：标准错误码、任务结束事实的设计评估。
- `app/collectors/service.py`：统一成功、部分成功、最终失败、无有效数据的状态归纳；写回源健康摘要。
- `app/collectors/weibo_octopus_collector.py`：将 HTTP 认证失败、Token 缺失/失效、业务响应错误分别映射为错误码。
- `app/core/scheduler.py`：仅调用健康策略；认证失败源进入低频探测，不影响其他源。
- `app/api/admin_data_sources.py`：返回健康摘要、过滤和受限测试接口。

不建议在 scheduler 中直接写业务字段，也不建议在管理 API 请求时临时扫描全部运行记录作为唯一健康计算路径。

### 5.2 Phase 8-A 后端

涉及模块：

- `app/services/event/risk_service.py`：新增可解释事件评分计算与分项输出，保留原有最高分回退兼容。
- `app/services/event/heat_service.py`：保留热度算法，增加数据窗口、原因和缺失源说明；不要把热度直接等同风险。
- `app/services/event/aggregator.py`：继续负责成员关联，不在本阶段引入新聚类算法。
- `app/api/events.py` 与 `app/schemas/event.py`：事件详情返回画像、评分因素、数据新鲜度和来源态势。
- `app/services/propagation_service.py` 与相关 schema：保留接口，调整名称/说明和前端语义为来源时间态势。

建议只新增只读计算接口或在现有事件详情中扩展字段，不先新增写入流程。所有新增结果应带数据窗口和 `data_sufficiency`（充分/有限/不足）标记。

### 5.3 前端页面与组件

- `Sources.vue`：健康状态、错误码、最近成功、连续失败、人工提醒；保留运行历史入口。
- `CollectionLog.vue`：按源和错误码筛选，区分“任务失败”“任务成功但无有效数据”。
- `Events.vue`：列表增加数据充分性、热度趋势和事件级风险标签，避免只显示单条最高风险。
- `EventDetail.vue`：增加基本事实、来源/时间态势、风险因素、数据新鲜度和处置记录区。
- `Propagation.vue`：改为来源时间态势；真实传播关系未接入前隐藏确定性箭头或加“推断”提示。
- `CommandScreen.vue`：只展示经过状态和数据充分性校验的高风险事件；数据源异常应有全局提示，防止大屏空白被理解为无风险。

权限沿用现有 `sources:read`、`sources:write`、`events:read`、`events:write` 和审计机制。健康状态浏览可给研判人员，凭证、暂停、恢复和测试采集仅给管理员。

### 5.4 API 建议

不改变现有接口含义，优先扩展响应：

```text
GET  /admin/data-sources
GET  /admin/data-sources/{id}/runs
POST /admin/data-sources/{id}/test       （后续、管理员）

GET  /events
GET  /events/{id}
GET  /events/{id}/situation              （可选的只读态势接口）
POST /events/aggregate                   （保留现有聚合任务）
GET  /propagation/graph/{id}             （语义改为来源时间态势）
```

`/events/{id}/situation` 若实施，响应应包含：`risk`、`risk_factors`、`heat`、`trend`、`source_distribution`、`daily_counts`、`keyword_counts`、`data_window`、`data_sufficiency`、`stale_sources`。不输出未经证实的“传播者”或“影响人数”。

## 6. Phase 8-A 详细实施拆解

### A0：口径与兼容性确认（P0）

- 目标：锁定事件风险、热度、趋势和来源分类定义。
- 数据库：无。
- 后端：为风险/热度服务定义纯计算输入输出，不写生产数据。
- 前端：确认事件详情区块和传播页新文案。
- 测试：补充现有事件风险和热度边界样本的期望结果。
- 风险：旧接口消费者依赖 `risk_score` 最高值；先保留回退并在响应中增加版本/解释。

### A1：事件画像只读输出（P0）

- 目标：在不改变事件关系的前提下，输出来源、时间、关键词、风险因素和数据窗口。
- 数据库：无迁移，全部由 `EventOpinion` + `Opinion` 查询计算。
- 后端：扩展 `EventDetailResponse` 或新增只读态势服务；避免 N+1 查询，复用已有聚合。
- 前端：事件列表、事件详情、大屏使用同一字段口径。
- 测试：无成员、单成员、跨来源、无发布时间、历史事件、数据源异常标记。
- 风险：时间字段混用 `publish_time/created_at`；必须在接口中明确有效时间口径。

### A2：事件级风险影子计算（P0/P1）

- 目标：用新公式计算并展示“建议事件分”，暂不替换现有告警触发分。
- 数据库：无迁移；不回写历史 `Event.risk_score`。
- 后端：新增纯函数和解释结构，支持按事件/时间窗口计算。
- 前端：同时显示现行分和建议分，标记为影子结果，供研判人员校准。
- 测试：单条高风险不支配、数量增长变化、地域命中变化、样本不足、边界 0/40/70/100。
- 风险：双分数造成用户困惑；页面必须写清“当前告警分”和“影子事件分”。

### A3：来源时间态势收口（P1）

- 目标：停止把推断 parent 链展示为真实传播链。
- 数据库：无。
- 后端：维持旧 graph 接口兼容，补充 `inferred=true` 或新摘要接口。
- 前端：默认展示时间序列、来源分布和内容清单；真实箭头仅在后续有关系证据时启用。
- 测试：同源多条、跨源多条、无时间、重复事件和空事件。
- 风险：已有用户熟悉传播图；需要在页面和培训材料中解释调整原因。

### A4：验收与灰度（P1）

- 目标：用廊坊历史事件和近期人工样本验证画像与风险解释。
- 数据库：无数据变更；测试数据使用隔离环境或只读 fixture。
- 后端/前端：只读灰度，保留回滚开关。
- 测试：接口契约、权限、性能、空数据、采集源异常、前端回归。
- 验收指标：事件合并可解释率、风险因素可追溯率、信息源新鲜度可见率、事件页关键字段完整率。

## 7. 测试设计

### Phase 8-0

- Token 缺失、Token 过期、HTTP 401/403、HTTP 429、HTTP 5xx、超时、解析错误的错误码映射。
- 连续失败 1/2/3 次及成功恢复，状态从 `healthy → degraded → unhealthy → healthy` 的转换。
- 成功但 0 条、上游返回 0 条、全部准入过滤、重复率异常的区分。
- 多数据源一源失败时，其他源仍完成；调度器不重复运行；低频探测不产生重试风暴。
- 管理接口权限、敏感错误脱敏、审计记录、列表状态与运行历史一致性。

### Phase 8-A

- 事件无成员、单成员、多来源、跨地域、缺失发布时间的画像输出。
- 风险公式分项、权重、封顶、等级阈值和数据不足标记。
- 现有 `EventRiskService`、告警过滤和历史接口兼容。
- 传播页对推断关系的文案、空图、重复重建和真实数据预留。
- 前端事件详情、大屏、事件列表和权限回归。

## 8. 风险分析

### 数据源风险

- 八爪鱼凭证长期失效会造成微博盲区；健康状态必须明确显示“数据源不可用”，不能将空结果计为零舆情。
- 第三方接口返回结构变化可能被误判为无数据；解析错误必须单独分类并保留原始错误摘要。
- 低频政府网站天然可能长时间无新文，不能用统一无数据阈值处理所有来源。

### 事件研判风险

- 事件级分数替换单条最高分前，必须经历影子计算和人工校准。
- 新闻转载会扩大信息数量但不代表独立参与人数；当前阶段只能称“内容数量”，不能称“参与人数”。
- 传播树为推断关系；未经平台关系证据不得用于认定传播主体或责任主体。
- AI 摘要和规则结果均为研判辅助，不得作为事实或行政处置的唯一依据。

### 权限与合规风险

- 凭证、错误信息、源配置和测试采集必须限制在管理员权限。
- 事件详情可能包含敏感内容，导出、截图和操作日志应按现有 RBAC 审计。
- 未来账号字段仅保存事件研判所需最小资料，不建设全量个人画像。

## 9. 明确暂缓事项

- ES、Kafka、Flink、微服务拆分：当前规模和核心问题不需要，先完善数据语义和失败可见性。
- 图数据库和社交关系图：没有真实转发/关注关系，当前 `PropagationNode` 只能做时间态势。
- 全网爬虫、视频平台、OCR、ASR：合规、成本和质量治理均超过本阶段目标。
- 自动 AI 决策、自动升级、自动生成对外回应：政府场景必须保留人工确认和责任链。
- 多租户和复杂组织编排：现阶段先用区域内 RBAC、责任单位和操作审计满足需求。
- 新增微博评论业务：本方案明确不依赖它；应在 Phase 8-B 另行设计采集授权、字段、隐私与事件关联。

## 10. 预期结果

完成 Phase 8-0 后，管理员能够区分“源未运行、源认证失效、任务失败、任务成功但无有效数据、源质量下降”，并能在不影响其他来源的情况下处置单一故障。

完成 Phase 8-A 后，事件中心将从“内容聚合和单条最高风险展示”升级为“基本事实、来源时间态势、可解释风险和处置可见性”的区域研判工作台。系统仍是单体架构、仍使用 PostgreSQL，仍保留现有接口和数据兼容边界，但更符合河北廊坊公安/政府人员对数据可信、风险可追溯和事件可解释的实际要求。
